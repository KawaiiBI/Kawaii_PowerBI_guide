1. Objetivos y encaje en el DP-700

El módulo del ETL low-code

Objetivos: describir las capacidades de Dataflow, crear soluciones de ingesta/transformación e incluir un Dataflow en un pipeline. Cae sobre todo en el Dominio 2 (Ingest and transform).

🎯 Crítico: query folding, staging, Fast Copy, incremental refresh (buckets), CI/CD + Git y la elección Dataflow vs Notebook vs Pipeline.

2. ¿Qué es un Dataflow?

Un Dataflow es una herramienta ETL cloud, la forma low-code / visual de hacer ETL en Fabric usando Power Query Online. Extract (conectores), Transform (visual) y Load (a Lakehouse, Warehouse, SQL DB, etc.).

Necesitas...Herramienta
Interfaz low-code visual, reutilizar transforms, que analistas lo mantenganDataflow Gen2 ✅
Transformaciones complejas con código (Python, Spark)Notebook
Orquestar múltiples pasos con dependenciasPipeline
Copiar datos raw sin transformarPipeline con Copy Data

Soporta ETL (transforma en memoria y escribe curado) y ELT (Pipeline copia raw a bronze, Dataflow transforma a silver/gold). Fabric potencia ELT con Fast Copy + staging.

4. Beneficios y limitaciones oficiales

Beneficios: dimensiones consistentes, self-service para analistas, extraer una vez y reutilizar, simplificar complejidad, consistencia y calidad, integración low-code.

⚠️ Las 3 limitaciones (oro para el examen)

  • ❌ NO son un reemplazo del data warehouse.
  • ❌ NO soportan Row-Level Security (RLS). Aplica RLS en el semantic model o warehouse downstream.
  • ❌ Requieren workspace en Fabric capacity (F SKU o Trial).
⚠️ La trampa de RLS es clásica: "quiero aplicar RLS al Dataflow" → respuesta: no se puede, hazlo downstream.
🎨

5. Interfaz y conectores

Se crea desde Data Factory, Power BI workspace o el lakehouse (los tres crean el mismo objeto). La interfaz de Power Query Online tiene ribbon, panel de queries, Diagram View, Data Preview y Query Settings (Applied Steps).

Conceptos clave de queries

  • Duplicar (copia independiente) vs Referenciar (cambios en la original afectan).
  • Disable load: "helper queries" que no cargan a destino pero se referencian.

Cientos de conectores: BBDD relacionales, ficheros, storage (ADLS, Blob, S3), SaaS, nativos Fabric (Lakehouse, Warehouse, KQL) y Web/OData. Autenticación como cloud connections gestionadas centralmente.

🎯

6. Data destinations

Destinos: Lakehouse, Warehouse, SQL DB in Fabric, KQL Database, y Azure SQL, Azure Data Explorer, Synapse. Update method: Append o Replace.

✨ El destino es opcional: un dataflow sin destino preserva las transformaciones y puede usarse como source discoverable desde Power BI Desktop. Al cargar a Lakehouse por primera vez, puede crear la tabla automáticamente.
⚡

7. Query folding: el concepto más examinable

Traducir Power Query a queries nativas del source

Query folding = traducir tus transformaciones a SQL/KQL que se ejecutan en el source, no en el dataflow. Con folding se transfiere solo lo necesario: mejor rendimiento, menos CU, refresh más rápido.

Indicadores en Applied Steps

  • 🟢 Círculo verde relleno: paso folded.
  • ⚠️ Círculo naranja: no folded (se ejecuta local). Cuando un step deja de foldear, todos los siguientes tampoco.

Rompen folding: Table.AddIndexColumn, custom columns complejas, Table.Buffer, merges (según conector), loops. Suelen foldear: filter, select, group by simple, sort. Fuentes sin folding: CSV/Excel/JSON, REST APIs (no relacionales).

🎯 Maximizar folding: filtros primero, transformaciones simples al inicio, rompe folding solo al final, y usa staging para volver a foldear. Ve la native query con View Native Query.
🎨

8. Staging queries: el patrón ELT

Staging materializa el output de una query en el staging Lakehouse/Warehouse interno de Gen2. Filosofía "stage once, reference many": las queries downstream referencian la staged y foldean al staging SQL endpoint.

Beneficios

  • Compute pushdown al staging Warehouse (folding sobre SQL).
  • Evitar leer el source varias veces, habilitar transforms complejas, data quality, fan-out a múltiples destinos.
⚠️ Staging no siempre mejora: añade coste de storage + write. No lo actives si la query ya fold end-to-end o tiene una sola salida sin ramificaciones.
🎯 Patrón Extract Previous: right-click en el paso donde se rompe el folding → Extract previous → nueva query con los pasos que sí foldean → Enable staging. La parte inicial fold al source, la compleja al staging warehouse.
🚀

9. Fast Copy

Fast Copy acelera la ingesta con movimiento nativo paralelizado que bypasea el mashup engine. Benchmark oficial: Gen1 1h39, Gen2 sin Fast Copy 35min, Gen2 con Fast Copy 9min (11× más rápido, 83% menos CU).

Requisitos

  • Source compatible (ADLS Gen2, S3, Azure SQL...), transformaciones limitadas (solo folding), destino compatible (Lakehouse) y feature habilitada en Options → Scale.
⚠️ Antipatrón: no combines Fast Copy con transformaciones no-folding en la misma query. Patrón correcto: query 1 Fast Copy pura → staging; query 2 referencia y transforma. Verifica en detalles que Engine type = CopyActivity.
🧩

10. Modern Evaluator y otras capacidades

  • Modern Evaluator: acelera transforms heavy sobre conectores no-foldable (files, APIs). Automático, no hay que activarlo.
  • Optimized copy to Lakehouse (Preview): acelera la "última milla" staging → Lakehouse. Se activa en Options → Scale.
  • Partitioned Compute (Preview): paraleliza transforms across particiones en datasets grandes. Automático.
🔁

11. Incremental refresh

Refrescar solo lo que cambió

Requisitos: la query debe fully fold al source e incluir una columna DateTime / Date / DateTimeZone. Se activa con right-click en la query → Incremental refresh.

Los 4 settings

  • DateTime column para filtrar.
  • Extract data from the past: cuánta historia inicial (días/semanas/meses/años).
  • Bucket size: tamaño de cada bucket (pequeño = más granularidad pero más overhead).
  • Detect changes: columna para detectar cambios (max value).

Cómo funciona

Lee el max value de la columna, compara con el último refresh, procesa solo los buckets cambiados en paralelo y hace delete + insert por bucket. Solo afecta al rango del bucket.

⚠️ Update method: solo replace. Límites: 50 buckets por query, 150 por dataflow. No borra data fuera del rango. Si va más lento que full refresh, aumenta el bucket size.
🔀

12. CI/CD y Git integration

Gen2 soporta Git integration, deployment pipelines (dev → test → prod), workspace folders y Public APIs (preview).

🎯 Save reemplaza Publish (just-in-time publishing): al guardar, los cambios se publican para el siguiente refresh. Al guardar se hace validación "zero row" (si el schema no se determina en 10 min, falla).
⚠️ Post-Feb 2026: si el publish falla y el dataflow fue guardado después de esa fecha, el refresh falla (fail-fast) en vez de usar la última versión exitosa. El Power Automate connector no funciona con la versión CI/CD.
💰

13. Costes y consumo de CU

MotorRate
Standard Compute (mashup)12 CU/seg hasta 10 min, luego 1.5 CU/seg
Fast Copy1.5 CU/seg (~8× más barato por segundo)

Optimizar: usa Fast Copy, fold todo lo posible, staging solo cuando aporta, optimiza buckets, desactiva refreshes innecesarios y divide queries.

14. Trampas típicas

  • "Gen2 soporta RLS" → ❌ no, hazlo downstream.
  • "Funciona sin capacidad Fabric" → ❌ requiere F SKU o Trial.
  • "Todos los conectores soportan Fast Copy" → ❌ solo compatibles.
  • "Fast Copy + transforms complejas en la misma query" → ❌ rompe Fast Copy; divide en dos.
  • "Query folding siempre pasa" → ❌ depende del conector y transforms.
  • "Incremental refresh con cualquier query" → ❌ requiere folding + columna DateTime.
  • "Incremental borra data histórica fuera de rango" → ❌ en Gen2 no la toca.
  • "500 buckets por dataflow" → ❌ 50 por query, 150 por dataflow.
  • "Save y Publish son distintos en CI/CD" → ❌ Save = Publish.
  • "Un Dataflow debe tener destination" → ❌ es opcional.
  • "Staging siempre mejora" → ❌ añade coste; no si ya fold end-to-end.
  • "Dataflows reemplazan al Data Warehouse" → ❌ limitación oficial.
