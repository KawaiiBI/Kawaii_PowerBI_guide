1. Anatomía de un Eventstream

Un Eventstream crea un pipeline que ingesta, procesa y entrega events. Se diseña en un canvas visual drag-and-drop, sin código ni gestión de infraestructura. Tres componentes obligatorios: Sources (📥), Transformations (🔄) y Destinations (📤).

🎯 Crítico para el examen: las 5 windowing functions, derived streams para content-based routing, elegir Eventstream vs Spark Structured Streaming, SQL operator vs no-code, y DeltaFlow para CDC.
🎨

2. Enhanced vs Standard capabilities

Standard: versión original, sources/destinations limitados. Enhanced ⭐: moderna (recomendada), más sources y destinations, mejor UI, SQL operator y DeltaFlow. Para nuevos eventstreams, siempre Enhanced.

📥

6. SQL Code editor operator

Para teams code-first: escribes SQL directamente (misma sintaxis que Stream Analytics), con windowing, aggregations, joins y content-based routing en una query.

SELECT device_id, AVG(temperature) AS avg_temp, System.Timestamp() AS window_end
FROM IoT_Stream
WHERE temperature IS NOT NULL
GROUP BY device_id, TumblingWindow(minute, 5)

Con varios SELECT ... INTO haces routing a distintos destinos desde un solo operator.

⭐

7. Windowing functions: el corazón del streaming

Una window es un intervalo de tiempo sobre el que agrupas events para agregarlos. Necesarias porque los streams son infinitos (un GROUP BY clásico no aplica). Se usan en el GROUP BY.

🎯 Regla clave: todas las windows output events al FINAL de la window (un solo event por window, con la agregación, timestamped al end). Tamaño máximo: 7 días para todos los tipos.
🌸

8. Tumbling Window

Intervalos fixed, sin overlap, contiguos. Cada event cae en exactamente una window. 1 parámetro (size). Como muffins en una bandeja 🧁.

GROUP BY TollId, TumblingWindow(minute, 5)

Por defecto incluye el fin de la window (12:05) y excluye el inicio (12:00). Uso: hourly reports, 5-min rollups, daily aggregations.

🌸

9. Hopping Window

Como tumbling pero con overlap: "saltan" hacia delante. 3 parámetros: size, hop y (opcional) offset. Un event puede estar en varias windows.

GROUP BY Region, HoppingWindow(minute, 10, 5)  -- 10min, salta cada 5min
🎯 Un tumbling es un caso especial de hopping donde hop = size. Uso: rolling averages con updates frecuentes, dashboards smooth.
🌸

10. Sliding Window

Solo emite output cuando el content cambia (un event entra o sale). Es event-driven, no scheduled. Cada window tiene al menos 1 event. 1 parámetro (size). Como un detector de movimiento.

GROUP BY Topic, SlidingWindow(second, 10)
HAVING COUNT(*) >= 3

Uso: alerting (solo cuando cambia la condición), detección de patrones con timing irregular.

🌸

11. Session Window

Agrupa events que llegan cerca en el tiempo, filtrando periodos de inactividad. 2-3 parámetros: timeout, maximum duration y (opcional) partition. Como sesiones de conversación en WhatsApp.

Uso: user session tracking, device activity, anomaly detection por periodos.

🌸

12. Snapshot Window

Agrupa events con el mismo timestamp exacto (system time). Sin parámetros (el único). Uso: agrupar events simultáneos, cotizaciones del mismo tick.

🎯

14. Content-based routing con Derived streams

Content-based routing: enviar subsets del stream a distintos destinos según el contenido. Un derived stream es una versión transformada del stream original que lo habilita.

IoT_Sensors
  ├─ Filter temp>80  → Derived "HighTemps"  → Activator
  ├─ Aggregate hourly → Derived "HourlyAvg" → Eventhouse
  └─ Pass-through     → Derived "AllReadings" → Lakehouse
🎯 Pregunta típica: "rutear transacciones de alto valor a alerting y todas al warehouse" → respuesta: derived streams para content-based routing. Un solo source, múltiples outputs sin duplicar ingesta.
🌊

15. DeltaFlow y Spark Structured Streaming

DeltaFlow (Preview) simplifica los CDC pipelines: en vez de Event Hubs + Stream Analytics con glue code, lo hace todo en la config del connector (auto-creation de tablas, auto schema evolution). Sources: Azure SQL DB, PostgreSQL, SQL Server on VM, Azure SQL MI. Desde feb 2026 también puedes procesar CDC con Eventstreams SQL.

EventstreamSpark Structured Streaming
EstiloNo-code / SQLPySpark code
Ideal paraIngesta + transforms simplesTransforms complejas + ML
SkillsLow-codeData engineering

Desde 2026 se pueden integrar: descubres el source en Real-Time Hub, autogenera PySpark, y combinas lo mejor de ambos.

16. Trampas típicas

  • "Tumbling y Hopping son lo mismo" → ❌ Tumbling sin overlap, Hopping con overlap.
  • "Un event solo pertenece a una window" → ❌ solo en Tumbling; en Hopping y Sliding puede estar en varias.
  • "Sliding emite a intervalos regulares" → ❌ es event-driven.
  • "Window máximo 24h" → ❌ 7 días para todos.
  • "Session no necesita parámetros" → ❌ timeout + max duration; el único sin params es Snapshot.
  • "Content-based routing requiere múltiples eventstreams" → ❌ un solo eventstream con derived streams.
  • "Union combina cualquier campo" → ❌ solo shared fields; los demás se dropean.
  • "Un eventstream = un destination" → ❌ múltiples en paralelo.
  • "SQL operator soporta cualquier SQL" → ❌ subset específico de streaming.
  • "DeltaFlow para cualquier database" → ❌ solo Azure SQL DB, PostgreSQL, SQL Server on VM, Azure SQL MI.
  • "El output de una window contiene todos los events" → ❌ un solo event por window con la agregación.
