1. Objetivos y encaje en el DP-700

Objetivos: describir el patrón medallion, identificar decisiones clave al planificarlo en Fabric, describir el serving del gold y las best practices de seguridad y gobierno. Aparece transversalmente en todos los dominios.

🎯 Crítico: las 3 capas y qué va en cada una, single vs multiple lakehouses/workspaces, Materialized Lake Views, star schema en gold, OneLake data access roles y serving (SQL endpoint vs semantic model).
🥇

2. ¿Qué es la medallion architecture?

Patrón de diseño para organizar los datos de un lakehouse en tres capas de calidad creciente. Es el enfoque recomendado por Microsoft para Fabric.

Source Systems
    ↓
🥉 Bronze  (raw landing → Data Engineers)
    ↓
🥈 Silver  (clean, integrated → Analysts + Data Scientists)
    ↓
🥇 Gold    (business-ready → Business Users)
🌸 Como cocinar: Bronze = ingredientes del mercado, Silver = ingredientes preparados, Gold = platos listos para servir. Cada capa mejora la calidad y preserva el raw como source of truth (coherente con ACID de Delta).
🎨

3. Las 3 capas en detalle

Bronze 🥉Silver 🥈Gold 🥇
PropósitoLanding rawCleansing + integraciónModelado business
ModificaciónNingunaSí (validación)Sí (agregación + star schema)
AudienciaData EngineersAnalysts + Data ScientistsBusiness Users
FormatosCualquieraDeltaDelta (star schema)
RetenciónLargaMediaCorta (agregados)

Bronze: landing de todos los datos sin modificar, source of truth, trazabilidad. Silver: standardizar formatos, quitar nulls, deduplicar, merge de fuentes, data quality rules. Gold: star schema, agregados a la granularidad de reporting.

💡

4. Por qué separar en capas

  • Cada equipo tiene lo que necesita sin interferir.
  • Resilience: si silver rompe, reprocesas desde bronze sin volver al source (caro/lento/inaccesible).
  • Trazabilidad y compliance: rastrear cualquier dato de gold hasta bronze.
  • Iteración independiente (loose coupling) y reutilización (múltiples silvers/golds del mismo origen).

Tradeoff: más storage, más compute y más complejidad, que se compensan en cualquier proyecto serio.

🔧

5. Adaptar la arquitectura

Las 3 capas son un starting point, no un dogma. Puedes añadir una landing antes de bronze, golds específicos por dominio (Gold-Finance, Gold-Marketing) o simplificar a 2 capas (raw + curated). Los nombres bronze/silver/gold son convención (también raw/cleansed/curated, L0/L1/L2). Lo importante: cada capa con propósito y audiencia claros.

🏢

6. Single vs multiple lakehouses vs workspaces

Multiple lakehousesMedioPermisos distintos por capa
Multiple workspacesAltoCompliance/regulatory, capacity aislada por capa
🎯 Con separate workspaces, cada uno puede tener su propia capacity: aísla el compute y evita que la ingesta pesada tumbe los reports de gold.

7. Schemas para organizar layers

Los schemas están habilitados por defecto en Fabric. Nombra bronze, silver, gold:

CREATE SCHEMA bronze;
CREATE SCHEMA silver;
CREATE SCHEMA gold;

-- Cross-schema query en el mismo lakehouse
SELECT f.order_id, d.customer_name, f.total_amount
FROM gold.fact_sales f
JOIN gold.dim_customer d ON f.customer_key = d.customer_key;

Beneficios: discoverability, permisos por schema, sin overhead de multiple lakehouses, queries más limpias y data quality checks entre capas.

🥉

8. Bronze layer a fondo

Raw landing zone: los datos llegan exactamente como los envió el source. Suele mantener tipos originales (a veces strings) y añadir metadata (ingestion_timestamp, source_file, _ingest_batch_id). No se deduplica (eso es silver).

Cómo cargar bronze

  • Source en cloud storage (OneLake, ADLS, S3, GCS): usa un OneLake shortcut (sin copia, sin pipeline, sync automático). ✅ Enfoque recomendado.
  • Otros (BBDD, APIs, on-prem): Pipelines con Copy Data, Dataflows Gen2 o Notebooks.

Retención larga (compliance, reprocesamiento). Considera particionar por fecha. Automatización fuerte (schedule o event triggers) con idempotencia.

🥈

9. Silver layer a fondo

Limpieza e integración: standardizar formatos, quitar nulls, deduplicar, joins de múltiples bronze, casting, business rules. Tres formas en Fabric:

  • Dataflows Gen2 (low-code, analistas Power BI).
  • Notebooks (código, lógica compleja, ML, joins big data).
  • Materialized Lake Views (SQL declarativo con auto-refresh).
from pyspark.sql.functions import col, upper, trim, to_date
silver_df = (spark.table("bronze.orders_raw")
    .withColumn("order_date", to_date(col("order_date"), "yyyy-MM-dd"))
    .withColumn("quantity", col("quantity").cast("int"))
    .withColumn("region", upper(trim(col("region"))))
    .filter(col("order_id").isNotNull())
    .filter(col("quantity") > 0)
    .dropDuplicates(["order_id"]))
silver_df.write.format("delta").mode("overwrite").saveAsTable("silver.orders")
🌟

10. Materialized Lake Views (feature clave)

Una Materialized Lake View se define en SQL y Fabric la mantiene actualizada automáticamente. Es como una vista, pero con los resultados persistidos como tabla Delta real.

CREATE MATERIALIZED LAKE VIEW silver.sales AS
SELECT order_id, customer_id,
       UPPER(TRIM(region)) AS region,
       CAST(order_date AS DATE) AS order_date,
       unit_price * quantity AS total_amount
FROM bronze.sales
WHERE order_id IS NOT NULL;
✨ La magia: a diferencia de una SQL view (rerun cada query), la MLV guarda los resultados y, aprovechando el Delta transaction log, actualiza solo las rows que cambiaron, sin schedules ni triggers.
⚠️ Solo SQL. Si necesitas Python, API calls, ML inline, UDFs complejas o SCD Type 2 con historial, usa notebook.
⭐

11. Gold layer y star schema

Gold modela para consumo de negocio, normalmente con star schema: fact tables (mediciones, alta cardinalidad, dimension keys + valores agregables) rodeadas de dimension tables (entidades descriptivas, baja cardinalidad). Puede haber múltiples golds desde el mismo silver (BI star, ML flat wide, finance aggregates).

Por qué star schema: menos joins → queries más rápidas, comprensible, mantenible y requerido para modelos semánticos de Power BI.

                          |
     dim_date --- fact_sales --- dim_product
                          |

12. Dimensiones especiales

  • SCD Type 1: sobrescribir (pierdes historia). Type 2: nueva fila con Valid_From/Valid_To/Is_Current y surrogate key (preserva historia).
  • Role-playing: una misma dimension usada varias veces con roles distintos (ej: dim_airport como Departure y Arrival). En Power BI, con USERELATIONSHIP.
  • Junk dimension: consolidar varias dimensions pequeñas de baja cardinalidad en una (producto cartesiano de combinaciones).
  • Degenerate dimension: dimension al mismo grain que el fact (ej: sales_order_number); se deja en el fact table.
🎯

13. Serving del gold

SQL endpointSemantic model
AudienciaSQL users, data scientistsPower BI users, business
InterfazT-SQL (read-only)DAX, reports
DataDirecto desde DeltaDirect Lake (o import)
Business logicViews y functionsMeasures, calculated columns
🎯 Direct Lake lee directamente los ficheros Delta en OneLake, sin importar copia ni refresh: performance de Import + fresh data como DirectQuery, sin duplicar storage. Requiere Fabric capacity o Power BI Premium.

Gold en Warehouse (alternativa): para equipos SQL-first o enterprise BI tradicional; T-SQL completo (INSERT/UPDATE/DELETE/MERGE) vs el SQL endpoint del lakehouse que es read-only.

🔐

14. Seguridad y gobierno por capa

Medallion crea una frontera natural de acceso. Dos niveles: workspace/item permissions y OneLake data access roles (granular, por tabla/folder dentro de un lakehouse).

  • Single lakehouse + schemas: OneLake data access roles por schema (ej: role_gold_readers solo a gold.*).
  • Multiple lakehouses: item permissions por lakehouse.
  • Multiple workspaces: workspace roles distintos, aislamiento máximo.
🎯 Cada lakehouse tiene el rol built-in DefaultReader (acceso a todo para usuarios ReadAll). Se puede modificar o borrar para restringir el acceso por defecto.
⚠️

15. Trampas típicas

  • "bronze/silver/gold son obligatorios" → ❌ son convención.
  • "Siempre 3 capas" → ❌ starting point; pueden ser 2, 4 o más.
  • "Bronze debe estar en Fabric" → ❌ puede ser un shortcut a ADLS/S3/GCS.
  • "Gold siempre es star schema" → ❌ lo más común, no obligatorio (flat wide para ML, etc.).
  • "Necesito 3 workspaces para medallion" → ❌ vale un solo lakehouse con schemas.
  • "MLV son solo para gold" → ❌ también silver o cualquier capa SQL-expressible.
  • "MLV funcionan con Python" → ❌ solo SQL.
  • "Direct Lake requiere refresh como Import" → ❌ lee directo de Delta, siempre current.
  • "OneLake data access roles reemplazan workspace roles" → ❌ los complementan.
  • "DefaultReader no se puede tocar" → ❌ se puede modificar o borrar.
  • "El default semantic model = custom" → ❌ desde sept 2025 ya no se crean automáticamente.
