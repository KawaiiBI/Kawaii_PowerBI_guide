1. Objetivos y encaje en el DP-700

Inicio de la Fase 2 (Real-Time Intelligence). Objetivos: describir real-time analytics, entender los componentes de RTI, ingestar y transformar data-in-motion, almacenar y consultar en KQL, visualizar con Real-Time Dashboards y automatizar con Activator.

🎯 Crítico: diferencia real-time vs batch, los 6 componentes, eventstream vs direct ingestion, KQL fundamental, update policies vs materialized views vs stored functions, OneLake availability, Eventhouse endpoint y Activator.
⚠️ Si vienes de DP-600, RTI es lo más nuevo para ti. Prepárate para KQL, es distinto al SQL pero muy intuitivo. ✨
⚡

2. ¿Qué es real-time analytics?

Procesar, analizar y actuar sobre datos según se generan (segundos/minutos). En realidad es near real-time: siempre hay latencia. Sub-second = real-time; 1-10s = near real-time típico; horas/días = batch.

BatchReal-time
CadenciaHoras/díasSegundos/minutos
DatosSnapshots históricosFluyen continuamente
Uso típicoReports diarios/mensualesAlertas, monitoring, actions

Casos: delivery tracking, equipment monitoring, fraud detection, website performance, system health. Batch y real-time coexisten.

🎪

3. Events y streams

Un event es un record de algo que ocurrió (click, compra, lectura de sensor). Un stream es una secuencia de events ordenados por tiempo, que fluyen continuamente.

🌷 Un event es como una carta en el buzón; un stream es el cartero pasando cada día. Los streams son el mecanismo de entrega de los events.
🌸

5. Real-Time Hub

Catálogo central de toda la data-in-motion a la que tienes acceso. Organiza: Data sources, Azure sources (IoT Hub, Service Bus), Fabric events (job status, OneLake, workspace items) y Azure events (Blob Storage). Desde el Hub puedes previsualizar streams, navegar a eventstreams/KQL, crear Activator rules y suscribirte a eventos.

🚰

6. Eventstreams (introducción)

Un Eventstream trae real-time events a Fabric, los transforma y los rutea. Como tuberías: source → transformations → destination. Sources: Event Hubs, IoT Hub, CDC, Kafka, GCP Pub/Sub, MQTT. Transformaciones: Filter, Manage fields, Aggregate, Group by, Union, Join, Expand, SQL code editor. Destinos: KQL DB, Lakehouse, Derived stream, Activator, Custom endpoint.

🎯 Usa Eventstream cuando quieras transformaciones declarativas o routear a múltiples destinos. Para direct ingestion sin transformación o transforms complejas con PySpark, otras opciones.
🏛️

7. Eventhouse y KQL Database

Un Eventhouse es un contenedor que hospeda múltiples KQL databases, comparte capacity y da monitoring unificado. Compute disponible en 5-10 segundos (más rápido que Spark pools en startup).

Una KQL Database es un data store real-time optimizado (motor Kusto), ideal para time-series. Contiene tables, stored functions, materialized views, shortcuts y data streams. Soporta RLS, CLS y OLS. Un KQL Queryset es la colección de queries (multi-tab, save, share, KQL + subset de T-SQL).

🌸

8. Fundamentos de KQL

KQL usa pipes (|) para encadenar operaciones, de izquierda a derecha.

stock
| where ["time"] > ago(5m)
| summarize avgPrice = avg(todouble(bidPrice)) by symbol
| project symbol, avgPrice
KQLSQL
stock | take 10SELECT TOP 10 * FROM stock
stock | where symbol == "MSFT"WHERE symbol = 'MSFT'
stock | summarize avg(price) by symbolGROUP BY symbol
⚠️ KQL usa == (no =), strings en comillas dobles, y bin() para buckets temporales. KQL databases también soportan un subset de T-SQL (para queries simples o migración).
⚙️

11. Activator

Automated processing de events que triggerean actions. 4 core concepts: Events (records), Objects (business entities), Properties (fields mapeados) y Rules (condiciones → action). Actions: notificaciones (email, Teams), workflows Power Automate, pipelines y notebooks.

🎯 Activator puede ser destination de un eventstream: los events fluyen y las rules deciden las acciones. Es mucho más que solo enviar emails.
🎯

12. Direct ingestion vs eventstream

Dos formas de ingestar: con eventstream (transformación in-flight, routing a múltiples destinos) o direct ingestion a KQL (raw, simple, bulk loads). Con direct ingestion, las transformaciones se hacen post-storage con update policies.

🎯 Diferencia crítica: eventstream transformations = pre-storage (in-flight); update policy transformations = post-storage (after ingestion).
🌊

13. OneLake availability

Feature del Eventhouse que hace que los datos KQL estén también disponibles en OneLake en formato Delta Parquet, para que otros workloads (Lakehouse, Direct Lake, notebooks) los consuman. Dos copias sincronizadas: una para KQL, otra para el resto de Fabric.

⚠️ Hay que activarla manualmente (por database o tabla). Usa adaptive parquet batching (hasta 3h de delay por default, TargetLatencyInMinutes de 5min a 3h). Bajar mucho el delay → many small files → lecturas ineficientes, y la tabla resultante es read-only.
🎯

14. Eventhouse endpoint

Permite consultar tablas de Lakehouse o Warehouse desde un Eventhouse con la velocidad del motor KQL. Instant schema sync (segundos), mirrored schema, consumo enriquecido (SQL, Notebook, Copilot, NL2KQL). Bajo el capó usa shortcuts + query acceleration policies, sin duplicar datos. En 10 segundos está sincronizado; mejora al cachear más.

🎯 Caso típico: Lakehouse con ventas históricas → activas el endpoint → time-series analysis avanzado con KQL (anomaly detection, Python) sin duplicar datos.
💰

15. Facturación, capacity scheduler y throttling

Compute: por Eventhouse UpTime. Storage en 2 tiers: OneLake Cache Storage (premium, fastest queries, la cache policy) y OneLake Standard Storage (persistente, la retention policy). Con Capacity Scheduler (minimum configurado), la cache storage se incluye en los capacity charges.

Los 3 niveles de throttling

LevelIngestionQueriesData loss
Proactive✅ Continúa⚠️ Throttled❌
Reactive⚠️ Pausada⚠️ Pausada❌
Extreme reactive⚠️ Pausada⚠️ Pausada⚠️ Posible

16. Trampas típicas

  • "Real-time = 0ms" → ❌ near real-time, siempre hay latencia.
  • "Eventstream = KQL database" → ❌ eventstream ingesta/transforma/rutea; KQL DB almacena/consulta.
  • "Direct ingestion siempre mejor" → ❌ no permite transformaciones pre-storage.
  • "KQL = SQL" → ❌ pipes, ==, flow-based.
  • "OneLake availability activa por defecto" → ❌ hay que activarla.
  • "Bajar TargetLatencyInMinutes siempre mejor" → ❌ many small files; la tabla es read-only.
  • "Eventhouse endpoint copia datos" → ❌ usa shortcuts + query acceleration.
  • "Throttling siempre pierde datos" → ❌ solo extreme reactive.
  • "Activator solo envía emails" → ❌ también pipelines, notebooks, workflows.
  • "Materialized views KQL = Materialized Lake Views" → ❌ implementaciones distintas.
  • "Real-Time Dashboard consulta cualquier source" → ❌ diseñado para KQL databases.
