2. ¿Qué es Delta Lake exactamente?

Semántica de base de datos sobre el data lake

Delta Lake es una storage layer open-source que hace que un montón de ficheros Parquet se comporten como una tabla de base de datos (transacciones, schema, versiones). En el Lakehouse explorer las tablas Delta llevan el icono triangular Δ. En Fabric, todas las tablas de un lakehouse son Delta por defecto.

🌷 Analogía kawaii: Parquet son hojas sueltas; Delta Lake las encuaderna con un índice detallado y un registro de cambios. Ahora puedes actualizar, versionar y auditar.
🩺

3. Anatomía de una tabla Delta

Datos (Parquet) + transaction log

Tables/mi_tabla_delta/
├── part-00000-....snappy.parquet   ← Datos (Parquet, inmutables)
├── part-00001-....snappy.parquet
└── _delta_log/                     ← Transaction log
    ├── 00000000000000000000.json   ← Cada operación = 1 JSON
    └── ...checkpoint.parquet       ← Checkpoint cada N versiones

Los Parquet son inmutables (cada cambio genera ficheros nuevos). El _delta_log registra qué ficheros están activos en cada versión.

🎯 ¿Cómo se hace UPDATE si Parquet es inmutable?

Delta usa copy-on-write: lee los ficheros afectados, escribe ficheros nuevos con las filas actualizadas y marca los viejos como removidos en el nuevo JSON del log. Por eso se acumulan ficheros pequeños (que resolvemos con OPTIMIZE), y los viejos habilitan time travel hasta que hagas VACUUM.

✨

4. Los 5 grandes beneficios de Delta

Los 5 puntos oficiales

  • 🎯 Tablas relacionales con CRUD: CREATE, SELECT, INSERT, UPDATE, DELETE, MERGE sobre tu data lake.
  • 🎯 Transacciones ACID: varios notebooks escriben a la misma tabla sin corromperla.
  • 🎯 Versionado y time travel: historial completo, consultar el pasado, auditar, recuperar errores.
  • 🎯 Batch y streaming: Delta puede ser sink o source de un stream con la misma API.
  • 🎯 Formato estándar: Parquet por debajo, interoperable con el SQL endpoint, Databricks, Snowflake, etc.
🛠️

5. Crear tablas Delta: 5 formas

# 1) saveAsTable desde un DataFrame (el más común, managed)
df.write.format("delta").saveAsTable("mytable")

# 2) saveAsTable con path (external)
df.write.format("delta").saveAsTable("myext", path="Files/myext")

# 3) DeltaTableBuilder (tabla vacía con schema)
from delta.tables import *
DeltaTable.create(spark).tableName("products") \
  .addColumn("ProductId", "INT").addColumn("Price", "FLOAT").execute()

# 5) Escribir Delta sin registrar en el catálogo
df.write.format("delta").save("Files/mydatatable")
-- 4) SQL CREATE TABLE
CREATE TABLE salesorders (OrderId INT, SalesTotal FLOAT) USING DELTA;
✨ Automatic table discovery: si guardas Delta en Tables/nombre/ (en vez de Files/), Fabric crea el metadata automáticamente, sin saveAsTable.

7. Operaciones: SELECT, INSERT, UPDATE, DELETE

Relacional completo con Spark SQL o Delta API

SELECT * FROM products WHERE Category = 'Bikes';
INSERT INTO products VALUES (1, 'Widget', 'Accessories', 2.99);
UPDATE products SET ListPrice = 2.49 WHERE ProductId = 1;
DELETE FROM products WHERE Discontinued = true;
from delta.tables import *
# Por nombre (catálogo) o por ruta
dt = DeltaTable.forName(spark, "products")
dt.update(condition="Category = 'Accessories'", set={"Price": "Price * 0.9"})
dt.delete(condition="Discontinued = true")

Usa Spark SQL para catalog tables y lógica declarativa; usa la Delta API (forPath/forName) para datos por ruta y operaciones programáticas complejas.

👑

8. MERGE INTO: el rey del upsert

INSERT + UPDATE + DELETE en una operación atómica

MERGE INTO people10m t
USING people10m_updates s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *

Cláusulas: WHEN MATCHED, WHEN NOT MATCHED y WHEN NOT MATCHED BY SOURCE (útil para deletes de sincronización). Con condiciones (AND) haces UPDATE/DELETE/INSERT selectivos. Sin WHEN MATCHED, el MERGE actúa como deduplicación (exactly-once).

🎯 SCD Type 1 (sobrescribir) vs Type 2 (historial)

SCD Type 1SCD Type 2
Historial❌ No preservado✅ Preservado (filas versionadas con Valid_From/To, Is_Current)
DeletesFísicosSoft (Is_Current=false)
ComplejidadBajaAlta
Uso típicoReporting operacionalAuditoría, compliance
⚠️ Si el source tiene filas duplicadas que hacen match con la misma fila del target, MERGE falla. Deduplica el source antes: source.dropDuplicates(["id"]). En Fabric, Copy Job soporta SCD Type 2 nativamente (preview).

9. Schema evolution

Modificar el schema sin romper compatibilidad

# Añadir columnas nuevas del source al escribir
new_df.write.format("delta").mode("append").option("mergeSchema", "true").saveAsTable("products")
# Sobrescribir el schema completo (con cuidado)
df.write.format("delta").mode("overwrite").option("overwriteSchema", "true").saveAsTable("products")
MERGE WITH SCHEMA EVOLUTION INTO sales AS target
USING staged_sales AS source ON target.order_id = source.order_id
WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *;
⚠️ Por defecto Delta enforcea schema (rechaza escrituras que no cumplen). Schema evolution hay que activarlo explícitamente con mergeSchema=true o config. Es buena práctica: solo actívalo cuando de verdad quieras cambios.
⏰

10. Time travel y DESCRIBE HISTORY

DESCRIBE HISTORY products;                       -- historial de versiones
SELECT * FROM products VERSION AS OF 0;          -- por versión
SELECT * FROM products TIMESTAMP AS OF '2026-01-01T00:00:00';  -- por timestamp
RESTORE TABLE products TO VERSION AS OF 3;       -- rollback
⚠️ El time travel funciona mientras existan los ficheros viejos. Tras un VACUUM más allá del retention, ya no puedes viajar a esas versiones. Propiedades: delta.logRetentionDuration (30 días) y delta.deletedFileRetentionDuration (7 días).
⚡

11. OptimizeWrite, OPTIMIZE y V-Order

El "small files problem" y sus soluciones

Muchas escrituras pequeñas acumulan muchos ficheros minúsculos y ralentizan las lecturas. Tres features lo resuelven:

FeatureCuándo actúaObjetivoDefault en Fabric
OptimizeWriteAl escribirPrevenir small files✅ ON
OPTIMIZEManual/scheduledConsolidar ficheros existentesManual
V-OrderAl escribirAcelerar lecturas✅ ON
 
OPTIMIZE products;
OPTIMIZE products ZORDER BY (Category);   -- co-localizar por columna
🎯 V-Order: exclusivo de Fabric, activado por defecto. Overhead ~15% al escribir, gran beneficio en lecturas (Power BI y SQL endpoint lo aprovechan al máximo). Es 100% Parquet compliant. Desactívalo solo en staging bronze write-intensive.
🧹

12. VACUUM: limpieza y sus peligros

Elimina físicamente los ficheros obsoletos

VACUUM borra los Parquet ya no referenciados y más antiguos que el retention. No borra el transaction log. Default: 7 días (168h), y el sistema impide bajarlo por debajo.

VACUUM products RETAIN 168 HOURS;   -- 7 días
VACUUM products RETAIN 720 HOURS;   -- 30 días (más seguro)
⚠️ Bajar de 7 días rompe el time travel y puede corromper lecturas concurrentes. Solo se puede desactivando retentionDurationCheck, nunca en producción sin entender las consecuencias.
📁

13. Particionado en tablas Delta

df.write.format("delta").partitionBy("Category").saveAsTable("partitioned_products")

Beneficio: partition pruning / data skipping (Delta lee solo las particiones relevantes al filtrar por la columna).

⚠️ Particiona por baja cardinalidad (year, country, category), nunca por alta (user_id, order_id, timestamp): generas miles de ficheros pequeños. Regla: ~1 GB por partición, no más de unos cientos de particiones. Alternativas modernas: Liquid Clustering y Z-ORDER.
🌊

14. Streaming: Delta como source y sink

Structured Streaming con Delta

# Delta como SINK (destino de un stream)
stream_df.writeStream.format("delta") \
    .option("checkpointLocation", "Files/checkpoints/iot") \
    .start("Tables/iot_readings")

# Delta como SOURCE (leer una tabla como stream)
s = spark.readStream.format("delta").option("ignoreChanges", "true").table("orders_in")
⚠️ Como source, por defecto solo procesa appends; para UPDATE/DELETE del source usa ignoreChanges o ignoreDeletes. El checkpointLocation es crítico: único por stream, permite recuperarse de fallos. Para MERGE desde un stream, usa foreachBatch (con MERGE idempotente).

Output modes: append (default), update, complete. Casos: IoT, CDC, clickstream, log processing.

⚠️

15. Trampas típicas

  • "UPDATE modifica el Parquet en sitio" → ❌ los Parquet son inmutables; genera ficheros nuevos.
  • "Time travel funciona para siempre" → ❌ solo mientras existan los ficheros viejos.
  • "OPTIMIZE incluye VACUUM" → ❌ son operaciones distintas.
  • "OptimizeWrite = OPTIMIZE" → ❌ OptimizeWrite es preventivo al escribir; OPTIMIZE es mantenimiento post-hoc.
  • "V-Order hay que activarlo" → ❌ está activado por defecto.
  • "MERGE acepta duplicados en el source" → ❌ falla; deduplica antes.
  • "En streaming no necesito checkpointLocation" → ❌ es crítico; único por stream.
  • "Un stream desde Delta procesa UPDATEs" → ❌ solo appends por defecto (usa ignoreChanges/ignoreDeletes).
  • "Schema evolution es automático" → ❌ por defecto se enforcea; actívalo con mergeSchema.
  • "DROP de una external borra los datos" → ❌ solo el metadata.
  • "V-Order es propietario y no lo lee nadie más" → ❌ es 100% Parquet compliant.
