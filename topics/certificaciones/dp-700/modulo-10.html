1. Eventhouse y KQL databases

Un Eventhouse es un contenedor que hospeda una o más KQL databases (tables, stored functions, materialized views, data streams, shortcuts). Al crear un Eventhouse se crea automáticamente una default database con el mismo nombre; puedes crear más para separar dominios, permisos o retention distintos.

🎯 Crítico: KQL optimization (filter early, project early, join order), materialized view vs stored function vs update policy, todas las policies, RLS, cache y retention.
📥

2. Ingesta y database shortcuts

Formas de ingestar (menú Get Data): local files, Azure Storage/S3, Eventstream, Event Hubs/IoT Hub, OneLake, Data Factory Copy, Dataflows y connectors (Kafka, Flink, MQTT, Kinesis, Pub/Sub).

Database shortcuts: referencias a KQL databases existentes (otros eventhouses o ADX) para consultar sin copiar. A diferencia de los OneLake shortcuts (apuntan a files/folders), los database shortcuts apuntan a KQL databases completas.

📝

3. KQL Queryset y render

El queryset (embedded o standalone) permite save queries, multi-tab, share, KQL + T-SQL y visualizaciones inline con el operador | render.

TaxiTrips
| summarize count() by taxi_id
| top 10 by count_
| render columnchart
🌸

4. KQL fundamental

Pipes (|) encadenan operaciones de izquierda a derecha. El orden importa.

OperadorFunción
whereFiltrar rows
projectSeleccionar columnas
extendColumnas calculadas
summarizeAgregar (GROUP BY)
top / takeTop N con orden / N rows
join / unionUnir tablas

Funciones temporales: ago(30min), bin(timestamp, 5m). Strings: has (whole-word, indexado, más rápido) vs contains (substring).

🎯

5. Case sensitivity (CRÍTICO)

⚠️ KQL es case-sensitive para TODO: table names, column names, function names, keywords y string values. Si la tabla es TaxiTrips, taxitrips falla. Para igualdad case-insensitive usa =~.
| where vendor_id == "VTS"   // match exacto
| where vendor_id =~ "vts"   // case-insensitive
🔍

6. Filter early

Cuanto menos data procese la query, más rápido va. Filtra primero (sobre todo por tiempo, que usa el índice) y ordena los filtros por selectividad (el que elimina más, primero).

TaxiTrips
| where pickup_datetime > ago(1d)   // time filter primero
| where vendor_id == "VTS"
| where fare_amount > 0
| summarize trip_count = count()
📏

7. Reduce columns early

project solo las columnas que necesitas reduce el uso de recursos, sobre todo en wide tables. Combina filter early + project early.

TaxiTrips
| where pickup_datetime > ago(30min)
| project trip_id, vendor_id, fare_amount
| summarize avg_fare = avg(fare_amount) by vendor_id
📊

8. Optimizar aggregations

Limita results al explorar, usa top N en vez de sort + take (está optimizado), y agrupa varias aggregations en un solo summarize.

TaxiTrips
| summarize trips = count(), avg_fare = avg(fare_amount), max_fare = max(fare_amount)
  by vendor_id
| top 10 by trips desc
🔀

9. Optimizar joins (el orden importa)

🎯 Regla clave: la tabla más pequeña primero (KQL procesa la primera para hacer match con la segunda). Y filtra ambas antes del join.
VendorInfo
| where region == "NY"
| join kind=inner (
    TaxiTrips
    | where pickup_datetime > ago(1d)
) on vendor_id

Tipos: inner (default), leftouter, fullouter, leftanti/rightanti, leftsemi, innerunique.

⭐

10. Materialized views a fondo

Precomputan aggregations que se actualizan automáticamente conforme llega data. Consisten en dos partes: materialized part (precomputada) y delta (data nueva). Al consultar, el sistema combina ambas → resultado siempre current. Un background process mueve delta → materialized.

.create materialized-view TripsByVendor on table TaxiTrips
{
    TaxiTrips
    | summarize trips = count(), avg_fare = avg(fare_amount) by vendor_id
}

Se consulta como una tabla normal. El query dentro debe ser un summarize.

🌸 Como un contador de galletas: en vez de contarlas todas cada vez, mantienes el cartel actualizado y sumas 1 cuando llega una nueva. Preguntar es instantáneo.
🔧

11. Stored functions

Encapsulan query logic reutilizable (con parámetros). No almacenan resultados, re-ejecutan cada llamada.

.create-or-alter function trips_by_min_passenger_count(num_passengers:long)
{
    TaxiTrips
    | where passenger_count >= num_passengers
    | project trip_id, pickup_datetime
}
// Llamar:
trips_by_min_passenger_count(3) | take 10
Materialized viewStored function
Almacena resultado✅ Sí (precomputed)❌ No
Re-ejecuta al llamar❌ No (combina partes)✅ Sí
Ideal paraAggregations frecuentesQuery logic reutilizable

12. Update policies

Automation que se triggerea al ingestar data a una source table: ejecuta una query para transformar y guarda el resultado en una destination table. No es schedule-based.

[{
  "IsEnabled": true,
  "Source": "RawLogs",
  "Query": "RawLogs | extend timestamp = todatetime(parse_json(payload).timestamp) | project timestamp, level, message",
  "IsTransactional": true
}]
⚠️ Con .set-or-replace la data en las derived tables también se reemplaza y puede perderse data. Recomendación: usa .set-or-append. Si la tabla tiene RLS, la update policy necesita ManagedIdentity.
📚

13. Todas las policies

PolicyPropósito clave
RetentionEliminar data vieja automáticamente (SoftDeletePeriod)
CacheQué va en premium cache (hot = 7d)

Restricted view accessCapa extra de permisos

Streaming ingestionData queryable casi inmediata (más overhead)
PartitioningDivide data para pruning
MergeConsolida extents pequeños (como OPTIMIZE de Delta)
Sharding / Ingestion time / Managed identityCómo se crean extents / timestamp auto / control de MI
🎯 Cache ≠ Retention: la cache policy controla qué está en el premium cache (performance); la retention policy es la que elimina datos. La cache no borra nada.
🔐

14. Row-Level Security y seguridad

RLS filtra las rows visibles por user con una query (normalmente una stored function). Force temporal para testing: set query_force_row_level_security;. Requiere Table Admin.

⚠️ RLS no funciona en External Tables, no puede referenciar otras tablas con RLS ni de otras databases, y es mutuamente excluyente con Restricted view access policy. En Fabric KQL solo hay filter predicates (no block).
⚠️

15. Trampas típicas

  • "KQL es case-insensitive" → ❌ case-sensitive para TODO.
  • "Materialized views se actualizan al schedule" → ❌ automáticamente al llegar data.
  • "Materialized views devuelven data desactualizada" → ❌ siempre current (materialized + delta).
  • "Update policies corren en schedule" → ❌ triggerean al ingestar.
  • "Stored functions almacenan resultados" → ❌ almacenan la query logic.
  • "RLS + restricted view access juntos" → ❌ mutuamente excluyentes.
  • "RLS funciona en External Tables" → ❌ no.
  • "Cache policy elimina datos" → ❌ eso es la retention policy.
  • "En joins el orden no importa" → ❌ tabla pequeña primero.
  • "Streaming ingestion siempre mejor" → ❌ más overhead; batch es más barato.
  • "Cada Eventhouse tiene una sola KQL database" → ❌ puede tener varias.
  • "has y contains son iguales" → ❌ has es whole-word indexado (más rápido).
  • "Materialized view sobre cualquier query" → ❌ debe ser summarize.
