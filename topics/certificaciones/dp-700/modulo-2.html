2. ¿Qué es un lakehouse en Fabric?

Data lake + data warehouse en uno

Un lakehouse es un item de storage que combina la flexibilidad del data lake (cualquier tipo de dato en su formato nativo) con la capacidad analítica del data warehouse (tablas con schema, transacciones ACID, consulta SQL). Puentea la brecha entre lake y warehouse trayendo capacidades de base de datos directamente sobre el data lake.

Vive en un workspace y sus datos se almacenan físicamente en OneLake (sobre ADLS Gen2).

¿Qué lo diferencia de un data lake tradicional?

  • Un metastore que registra qué carpetas son tablas.
  • Un formato de tabla (Delta Lake) con ACID, schema, versionado y time travel.
  • Un SQL analytics endpoint para consultar con T-SQL sin configurar nada.
  • Integración nativa con Power BI, notebooks y pipelines.
🎁

3. Qué se crea al crear un lakehouse (cambio 2025)

Aviso crítico: cambio de septiembre 2025

⚠️ Ya NO se crean 3 items. Desde el 5 de septiembre de 2025 los default semantic models ya no se crean automáticamente al crear un lakehouse, warehouse o mirrored item. Antes del 30 de noviembre de 2025 los existentes se desacoplaron como semantic models independientes.

Qué se crea AHORA (solo 2 items)

  1. 🏠 El lakehouse (Tables, Files y shortcuts).
  2. 🔎 El SQL analytics endpoint (auto-provisionado, read-only, T-SQL).

Si quieres un semantic model, tienes que crearlo tú explícitamente después.

🎯 En el examen: si una respuesta dice "se crean 3 items automáticamente", está desactualizada. Con la doc actual son 2 items.
📂

4. Estructura interna: Tables vs Files

Dos carpetas top-level

Tables: almacena tablas Delta Lake estructuradas y consultables. Soporta SQL vía endpoint, enforcea schema, ACID, Power BI y auto-optimización con V-Order. Automatic table discovery: cuando pones datos Delta en Tables, Fabric los registra solos. Limitación: solo formato Delta se registra como tabla.

Files: almacena datos raw en cualquier formato (CSV, JSON, Parquet, imágenes, PDFs...). Flexible para exploración y staging. NO enforcea schema, NO aparece en el SQL endpoint, pero Spark los lee.

Formato que se "ve como tabla"Solo DeltaCualquiera (no se registra)
Schema enforcement✅❌
Transacciones ACID✅❌
SQL analytics endpoint✅❌
Power BI Direct Lake✅❌
Uso típicoCurados, silver/goldRaw, staging, bronze

5. Delta Lake a fondo

La tecnología subyacente de todas las tablas

Delta Lake es un formato de tabla open-source (creado por Databricks) que aporta fiabilidad y capacidades relacionales sobre ficheros Parquet. En Fabric es el formato por defecto y la base de toda tabla del lakehouse.

Estructura física de una Delta table

Tables/mi_tabla/
├── part-00000-....parquet    ← Ficheros de datos (Parquet)
├── part-00001-....parquet
└── _delta_log/               ← Transaction log (JSON)
    ├── 00000000000000000000.json
    └── ...

Los datos son Parquet (columnar, comprimido) y el transaction log (_delta_log) registra cada cambio. Cada operación genera una entrada nueva en el log.

🌟 Los cuatro superpoderes de Delta Lake

  • 🎯 ACID: atomicidad, consistencia, aislamiento y durabilidad. Escrituras concurrentes desde varios notebooks sin corromper.
  • 🎯 Schema Enforcement: valida cada escritura; rechaza filas que no cumplen el schema. Previene schema drift.
  • 🎯 Time Travel: consulta versiones pasadas por número o timestamp. Por defecto 30 días.
  • 🎯 Updates/Deletes eficientes: UPDATE, DELETE y MERGE INTO (upsert).
# Time travel por versión
df = spark.read.format("delta").option("versionAsOf", 5).load("Tables/mi_tabla")
-- Time travel por timestamp
SELECT * FROM mi_tabla TIMESTAMP AS OF '2026-04-01T10:00:00'
🎯 V-Order (exclusivo de Fabric): optimización de escritura que reordena y comprime los Parquet para acelerar lecturas columnar (VertiPaq, Warehouse). Está activado por defecto. Añade algo de overhead al escribir pero acelera mucho las lecturas.

🎯 OPTIMIZE y VACUUM (mantenimiento)

OPTIMIZE mi_tabla;
OPTIMIZE mi_tabla ZORDER BY (columna_frecuente);
VACUUM mi_tabla RETAIN 168 HOURS;  -- retiene 7 días
⚠️ Trampa VACUUM: por defecto retiene 7 días (168h). No lo bajes por debajo: borrar ficheros recientes rompe el time travel y puede corromper lecturas concurrentes.
🔧

6. Managed vs External tables

Managed (el caso normal)

Fabric controla metadata y ficheros. Los datos van a Tables/, aparece en el explorer y si haces DROP TABLE se borran también los datos. Es el enfoque recomendado.

df.write.format("delta").saveAsTable("mi_tabla_managed")

External (con matices)

Fabric controla solo el metadata; los datos viven en otra ubicación. Si haces DROP TABLE se borra solo el metadata, los ficheros permanecen.

⚠️ Matiz oficial: los lakehouses soportan solo managed tables. CREATE TABLE ... LOCATION no está soportado. Para acceder a Delta tables en otro storage, la recomendación oficial es usar shortcuts, no external tables.
🎯 Regla de oro: "¿cómo accedo a datos Delta en ADLS desde un lakehouse?" → shortcut. "¿qué pasa al dropear una tabla?" → managed borra datos, external no.
🗄️

7. Lakehouse schemas (schema-enabled)

Agrupar tablas en colecciones nombradas

Los schemas agrupan tablas (como sales, marketing, hr), igual que en SQL Server. Al crear un lakehouse nuevo están habilitados por defecto y se crea el schema dbo.

Beneficios clave

  • 🎯 Organizar tablas por dominio.
  • 🎯 Control de acceso a nivel schema (permisos, RLS/CLS).
  • 🎯 Consultas cross-workspace con el four-part namespace: workspace.lakehouse.schema.table.
  • 🎯 Schema shortcuts para mapear un schema entero a otra carpeta con tablas Delta.
  • 🎯 Requisito de features avanzadas (materialized lake views).
-- Consulta cross-workspace con four-part namespace
SELECT * FROM ws_ventas.lh_gold.sales.orders;
⚠️ Limitaciones: un schema-enabled lakehouse NO se puede compartir directamente vía workspace sharing (usa shortcuts); external tables sobre ADLS no soportadas directamente; los lakehouses antiguos no tienen migración automática (prepárate usando four-part naming en el código).
📥

8. Ingesta de datos

Cinco métodos oficiales

  • Upload manual: pruebas y ficheros pequeños (van a Files).
  • Load to Table: CSV/Parquet a tabla Delta sin código (append u overwrite).
  • Dataflows Gen2: transformación low-code con Power Query (300+ conectores).
  • Notebooks: transformaciones complejas con código (PySpark, Spark SQL, Scala, R).
  • Data Factory pipelines: mover datos de fuentes externas con orquestación (Copy Data).
# Ingesta con notebook: CSV de Files a tabla Delta
df = spark.read.option("header", "true").csv("Files/mi_csv.csv")
df.write.format("delta").mode("overwrite").saveAsTable("mi_tabla")

9. Shortcuts en el lakehouse

Repaso de lo específico del lakehouse

  • En Tables: solo top-level; si es Delta se registra como tabla automáticamente.
  • En Files: cualquier nivel y formato, pero no se registra como tabla.
  • Tres tipos: table shortcut (una tabla Delta), schema shortcut (carpeta con varias tablas Delta) y Files shortcut (cualquier formato).

Ventajas: consultar entre workspaces/tenants sin duplicar, acceder a ADLS/S3/GCS sin ingesta, combinar multi-fuente sin ETL y reducir costes de storage.

🔄

10. Transformación: notebooks, dataflows, pipelines

Mismas herramientas, distinta filosofía

  • Notebooks (favorito del data engineer): PySpark, Spark SQL, Scala, SparkR; interactivos; Copilot genera código. Ideal para lógica compleja y ML.
  • Dataflows Gen2 (favorito del analista): Power Query M, low-code visual, 300+ conectores.
  • Pipelines (orquestación visual): Copy Data, Notebook, Dataflow, Stored Procedure con dependencias.
🎯 En el examen: "analistas familiarizados con Power Query que ingieren de SharePoint" → Dataflow Gen2. "data engineer con transformación Python + ML" → Notebook.
🔎

11. SQL analytics endpoint

Interfaz T-SQL read-only, auto-provisionada

El SQL analytics endpoint es una interfaz T-SQL read-only sobre las tablas Delta. Se auto-provisiona con cada lakehouse y corre en el mismo motor que el Warehouse. También lo tienen Warehouses, Mirrored databases, SQL databases y Cosmos DB en Fabric.

🎯 Es read-only sobre las tablas Delta

Puedes: SELECT, CREATE VIEW, CREATE FUNCTION, CREATE PROCEDURE, aplicar seguridad SQL (RLS, CLS, OLS). No puedes: INSERT/UPDATE/DELETE/MERGE ni CREATE/DROP TABLE sobre las auto-generadas. Para modificar datos, usa Spark.

Solo aparecen las tablas Delta. Los shortcuts en Tables que apuntan a datos Delta también aparecen.

🎯 Metadata sync (importantísimo)

Cuando cambias las tablas Delta desde Spark, un proceso background sincroniza el schema SQL. Es automático, con latencia de segundos a menos de un minuto, y se detiene tras 15 minutos de inactividad.

⚠️ Delays significativos: muchos lakehouses en el mismo workspace, muchos ficheros pequeños (fragmentación), alto volumen de cambios simultáneos o alta cardinalidad de particiones. Soluciones: separar lakehouses por workspace, OPTIMIZE regular y particiones de menor cardinalidad (~1 GB por partición).

🎯 Forzar refresh del metadata

Desde el portal (botón Refresh), vía REST API o con un stored procedure T-SQL.

POST https://api.fabric.microsoft.com/v1/workspaces/{workspaceId}/sqlEndpoints/{sqlEndpointId}/refreshMetadata
🎯 Patrón de pipeline: en Copy Data → Lakehouse → Dataflow que lee vía SQL endpoint, el dataflow puede leer datos viejos. Workaround oficial: añadir una Script activity entre la Copy y el Dataflow para forzar el sync.
💻

12. Query con Spark notebooks

Spark SQL vs PySpark

%%sql
SELECT * FROM sales.orders WHERE order_date >= '2026-01-01'
from pyspark.sql.functions import col
df = spark.table("sales.orders").filter(col("order_date") >= "2026-01-01")
display(df)

Spark SQL para lógica analítica pura; PySpark para lógica programática, funciones Python personalizadas y ML. Con schemas habilitados puedes hacer joins cross-workspace con el four-part namespace.

13. Power BI: Direct Lake y DirectQuery fallback

Direct Lake (modo por defecto)

Direct Lake lee directamente los Parquet de Delta sin importar ni copiar: rendimiento de Import, sin refresh y sin duplicar storage. Requiere capacidad Fabric (F SKUs) o Premium.

🎯 Direct Lake on SQL vs on OneLake

on SQL endpointson OneLake
RutaVia SQL endpointDirecto a ficheros Delta
Fallback a DirectQuery✅ Sí❌ NO
Si excede guardrailsFallback silenciosoError explícito (visuals fallan)
Recomendado para nuevos modelosSolo si necesitas fallback✅ Sí

🎯 Qué provoca DirectQuery fallback

RLS, DDM u OLS a nivel SQL en el endpoint; tabla basada en una SQL view no materializada; exceder los guardrails de la capacity; o no haber hecho refresh (framing) tras modificar la tabla Delta.

🎯 DirectLakeBehavior: Automatic (fallback silencioso, producción), DirectLakeOnly (error si falla, desarrollo), DirectQueryOnly (siempre DQ). Diagnostica con EVALUATE TABLETRAITS().
🔐

14. Seguridad del lakehouse

Niveles de acceso

  • Workspace roles: Admin, Member, Contributor, Viewer (todo el workspace).
  • Item-level sharing: acceso solo a un lakehouse concreto (ideal para analistas).
  • Sobre el SQL endpoint: RLS, CLS, OLS y Dynamic Data Masking (DDM).
  • Con schemas: permisos por schema.
  • Sensitivity labels de Purview que se propagan a items downstream.
⚠️ Aplicar RLS/CLS/OLS/DDM en el SQL endpoint puede provocar DirectQuery fallback en modelos Direct Lake on SQL. Si es posible, mueve la seguridad al semantic model.
⚠️

15. Trampas típicas y confusiones

Los errores clásicos del examen

  • "Al crear un lakehouse se crean 3 items" → desde sept 2025 solo 2 (lakehouse + SQL endpoint).
  • "Parquet o CSV en Tables se ven como tabla" → ❌ solo Delta. Hay que convertir (o Load to Table).
  • "Puedo modificar datos desde el SQL endpoint" → ❌ es read-only. Para escribir, Spark.
  • "Los cambios aparecen al instante en el SQL endpoint" → ❌ hay metadata sync; fuerza refresh si lo necesitas ya.
  • "External tables es la forma recomendada de acceder a datos externos" → ❌ la recomendación es shortcuts.
  • "Direct Lake siempre funciona" → ❌ puede hacer fallback a DirectQuery.
  • "V-Order hay que activarlo" → ❌ está activado por defecto.
  • "VACUUM se puede bajar de 7 días" → ⚠️ se puede pero rompe el time travel.
  • "Puedo compartir un schema-enabled lakehouse directamente" → ❌ usa shortcuts.

17. Mini-quiz de cierre

Autoevalúate con calma. Las soluciones las repasamos en la Guía Maestra de Tips y Trampas. 💕

Pregunta 1. Creas un lakehouse hoy (2026). ¿Cuántos items se crean automáticamente y cuáles?

  1. 3: lakehouse, SQL endpoint y default semantic model
  2. 2: lakehouse y SQL analytics endpoint
  3. 1: solo el lakehouse
  4. 4: lakehouse, SQL endpoint, semantic model y report

Pregunta 2. Una tabla creada con saveAsTable(..., path="Files/mi_tabla"). Ejecutas DROP TABLE. ¿Qué pasa?

  1. Se borran metadata y ficheros
  2. Se borra solo el metadata, los ficheros permanecen
  3. Falla porque no se pueden dropear external tables
  4. Solo si el usuario es Contributor

Pregunta 3. Aplicas RLS a nivel SQL sobre una tabla consumida por Power BI en Direct Lake. ¿Qué ocurre?

  1. El report falla con error de permisos
  2. La query hace fallback a DirectQuery automáticamente
  3. Sigue en Direct Lake ignorando el RLS
  4. Pide autenticación adicional

Pregunta 4. Tras un Copy Data de 1M filas, un Dataflow lee datos viejos vía SQL endpoint. ¿Causa y workaround?

  1. El pipeline falló. Reintentar
  2. El SQL endpoint está pausado. Iniciar sesión manual
  3. El metadata sync no ha terminado. Añadir Script activity para forzar sync
  4. Faltan permisos ReadData. Añadir Contributor

Pregunta 5. Sintaxis para consultar orders del schema sales en lh_gold del workspace ws_ventas desde otro workspace:

  1. lh_gold.sales.orders
  2. ws_ventas.lh_gold.sales.orders
  3. ws_ventas..sales.orders
  4. ws_ventas/lh_gold/sales/orders

Pregunta 6. Datos Delta en ADLS Gen2, quieres consultarlos sin copiar y con la recomendación oficial. ¿Qué haces?

  1. External table con CREATE TABLE ... LOCATION
  2. Pipeline con Copy Data
  3. Un shortcut a la carpeta ADLS en la sección Tables
  4. Dataflow Gen2 con conector ADLS

Pregunta 7. Tras un VACUUM en una tabla grande, las lecturas concurrentes fallan con "file not found". ¿Causa más probable?

  1. La tabla no es Delta
  2. Ejecutaste VACUUM RETAIN < 168h y borraste ficheros aún referenciados
  3. VACUUM requiere modo exclusivo
  4. Faltan permisos ReadAll

BONUS. Un modelo en Direct Lake on OneLake referencia una tabla con RLS a nivel SQL. Un usuario abre un report. ¿Qué ocurre?

  1. Fallback silencioso a DirectQuery, todo funciona más lento
  2. Se ejecuta en Direct Lake ignorando el RLS
  3. Los visuals fallan con error: Direct Lake on OneLake NO soporta fallback
  4. Se muestra el report con RLS aplicado
