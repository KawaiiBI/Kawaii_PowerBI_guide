1. Objetivos y encaje en el DP-700

Objetivos: describir capacidades de pipelines, usar Copy Data, crear desde templates y ejecutar/monitorizar. Aparecen transversalmente en los tres dominios.

🎯 Crítico: actividades más usadas (Copy Data, Dataflow, Notebook, Lookup, Get Metadata, ForEach, If), elección Pipeline vs Dataflow vs Notebook, triggers event-based con Activator, parámetros y dynamic content, retry logic y Copy Job.
🎼

2. ¿Qué es un pipeline?

Un pipeline encapsula una secuencia de actividades para mover y procesar datos. Es el director de orquesta: no transforma datos por sí mismo, coordina las actividades. Se diseña en un canvas gráfico, sin código.

Puede: mover datos, ejecutar transformaciones (dataflows, notebooks, SQL), orquestar con dependencias (success/failure/completion), aplicar lógica de control, ejecutarse por schedule o eventos, parametrizarse y notificar (Teams, Outlook, webhooks).

🧩

3. Componentes core

  • Actividades: tareas ejecutables. Cada una tiene un outcome (success, failure, completion, skipped) y se conectan según el outcome de la anterior.
  • Parámetros: input externo, se pasan al ejecutar, inmutables durante el run.
  • Variables: estado interno, mutables, se calculan durante el run.
  • Pipeline runs: cada ejecución con ID único. On-demand, scheduled o event-based.
🏷️

4. Las 3 categorías de actividades

  • Data movement: Copy Data, Copy Job.
  • Data transformation: Dataflow Gen2, Notebook, Spark Job Definition, Stored Procedure, SQL Script, Delete Data.
  • Control flow: loops, condicionales, esperas, invocación de pipelines.
🎯 Novedades Fabric vs ADF: Outlook, Teams, Semantic model refresh, Dataflow Gen2, Refresh SQL Endpoint, Lakehouse Maintenance.
🚚

5. Copy Data vs Copy Job

Copy Data es la actividad más usada: mueve datos de un source a un destino Fabric, sin transformar (o mínimo). Update methods según destino (Append, Overwrite, Upsert, Merge). Copy behavior de ficheros: PreserveHierarchy, FlattenHierarchy, MergeFiles.

6. Actividades de transformación

Cada una con su motor: Notebook y Spark Job Definition usan clusters Spark; Stored Procedure y SQL Script usan Azure SQL/Synapse/SQL Server/Warehouse; Copy Data, Dataflow y Delete Data usan compute de Fabric.

Notebook activity (la más flexible)

Ejecuta un notebook con base parameters que sobrescriben la celda con tag parameters. Notebook = interactivo (desarrollo); Spark Job Definition = script puro (producción).

8. Parámetros, variables y expressions

Las expressions empiezan con @. Referenciar: @pipeline().parameters.x, @variables('x'), @activity('Lookup1').output.value, @pipeline().RunId.

@utcnow()
@formatDateTime(utcnow(), 'yyyy-MM-dd')
@concat('Files/ingested/', pipeline().parameters.source_name, '/', formatDateTime(utcnow(), 'yyyy/MM/dd'), '/')
@if(equals(x, y), 'igual', 'distinto')
@length(myArray)   @contains(myArray, item)   @first(myArray)

9. Pipeline runs y triggers

  • On-demand: botón Run (guarda antes de ejecutar).
  • Scheduled: start/end date, time zone, frequency (Minute, Hour, Day, Week, Month) e interval.
  • Event-based: por eventos (fichero, job, workspace) usando Activator (ver siguiente sección).
🚨

10. Triggers event-based (Activator)

Ejecutan un pipeline automáticamente ante un evento en OneLake, Azure Blob Storage, jobs de Fabric o workspace. Arquitectura: fichero llega → evento emitido → Eventstream capta → Activator evalúa → pipeline se ejecuta.

Eventos típicos: Microsoft.Fabric.OneLake.FileCreated/FileDeleted, Microsoft.Storage.BlobCreated/BlobDeleted. Filtros por folder path o file name pattern (vía Subject).

🎯 Trigger parameters

@pipeline()?.TriggerEvent?.FileName
@pipeline()?.TriggerEvent?.FolderPath
⚠️ El ? es null-safe access: en run manual estos valores son NULL, y el ? evita que el pipeline falle al testear.
⚙️

12. Invoke Pipeline y Approval

Invoke Pipeline: ejecuta otro pipeline (modularizar, reutilizar, escapar del límite de 120 actividades). Patrón master + workers: Lookup lista de sources → ForEach → Invoke Pipeline por cada source.

Approval: pausa el pipeline y pide decisión humana (aprobar/rechazar) desde Teams o email. Approved → camino success; Rejected → failure. Queda auditable (quién y cuándo). Solo bloquea ese pipeline, no el workspace.

📊

13. Monitoring y notificaciones

Monitoriza desde el tab Runs del pipeline, el Monitor Hub (todos los pipelines) y la lista del workspace. Real-time con indicadores por actividad (verde/rojo/amarillo/gris). Run history con timestamps, duración, input/output por actividad, trigger y parámetros.

Failure notifications: por schedule (email), con Teams/Outlook activities en rama on-failure, o con Activator para acciones avanzadas.

🆚

14. Fabric vs Azure Data Factory

El concepto de pipeline, actividades y expression language es casi idéntico. Fabric añade: Outlook, Teams, Semantic model refresh, Dataflow Gen2, Refresh SQL Endpoint, Lakehouse Maintenance, Copy Job. Fabric cambia: Wrangling Data Flow → Dataflow Gen2. Los features nuevos de Fabric no se backportan a ADF (roadmaps separados).

⚠️

15. Trampas típicas

  • "Pipeline = dataflow" → ❌ pipeline orquesta, dataflow transforma.
  • "Copy Data es la única forma de mover datos" → ❌ también Copy Job, Dataflow, Notebook, Shortcuts, Mirroring.
  • "500 actividades por pipeline" → ❌ máximo 120 (incluidas anidadas).
  • "Retries automáticos" → ❌ desactivados por defecto.
  • "Parámetros = variables" → ❌ parámetros inmutables/externos, variables mutables/internas.
  • "Trigger parameters funcionan en run manual" → ❌ son NULL (por eso el ?).
  • "Timeout máximo 24h" → ❌ máximo 7 días (default 12h).
  • "Refresh SQL Endpoint refresca datos" → ❌ refresca el metadata sync del SQL endpoint del lakehouse.
  • "ForEach siempre en paralelo" → ❌ configurable (batch count default 20).
  • "Event triggers solo con OneLake" → ❌ también Azure Blob Storage.
  • "Secure I/O oculta datos en el destino" → ❌ solo en los logs.
